Engineering Methodology: How Local LLM VRAM & Token Speed Are Calculated

Deploying Large Language Models (LLMs) locally requires balancing three competing memory consumers inside your GPU's Video RAM (VRAM) or Apple Silicon Unified Memory: static model weights, the dynamic Key-Value (KV) attention cache, and framework runtime buffers. Relying on naive rules such as "1 billion parameters equals 1 GB" frequently leads to out-of-memory (OOM) crashes once long context windows are enabled.

1. Static Model Weights Footprint

Model weights represent the frozen neural network parameters stored on disk (typically in GGUF, EXL2, or SafeTensors format) and loaded directly into GPU memory. While unquantized FP16/BF16 weights require exactly 2.0 bytes per parameter, modern block-wise quantization formats such as Q4_K_M pack weights into roughly 4.85 bits per parameter on average due to super-block scaling metadata:

Weights VRAM (GB) = Parameters (Billions) × Bytes_Per_Parameter

2. Dynamic KV Cache Memory Scaling

During autoregressive inference, Transformer models cache intermediate Key and Value attention tensors for every token in the context window so previous tokens do not need to be recomputed. Unlike model weights, KV cache grows linearly with context sequence length and scales with the model's layer depth and hidden dimension:

KV Cache (GB) = (2 × Layers × Hidden_Dimension × Context_Tokens × KV_Bytes) ÷ 10⁹

Switching KV cache precision from FP16 (2 bytes) to Q8_0 (1 byte) or Q4_0 (0.5 bytes) via FlashAttention reduces context memory consumption by 50% to 75% with negligible perplexity degradation.

3. Runtime & CUDA/Metal Kernel Overhead

Inference engines (llama.cpp, vLLM, Ollama, ExLlamaV2) allocate workspace scratchpads, activation buffers, and CUDA/Metal context handles. Calcvora models this baseline allocation as 1.1 GB + 4.5% of the model weight footprint.

4. Memory-Bandwidth Token Speed Physics

For single-user local inference (batch size = 1), token generation is strictly memory-bandwidth bound rather than FLOPS bound. Generating a single output token requires streaming every active parameter from VRAM through the GPU's memory bus:

Estimated Speed (tokens/sec) = (GPU_Memory_Bandwidth_GB/s ÷ Active_Footprint_GB) × 0.75

Notice that Mixture-of-Experts (MoE) architectures like DeepSeek-V3 (671B total, 37B active) require enough VRAM to hold all 671B weights, but their generation speed depends only on the 37B active parameters read per token.

Worked Numerical Example: Running a 32B Reasoning Model on an RTX 3090

Suppose you want to deploy DeepSeek-R1-Distill-Qwen-32B using Q4_K_M quantization (0.62 bytes/param) at a 16,384-token context window on an NVIDIA RTX 3090 (24 GB VRAM, 936 GB/s bandwidth):

  1. Model Weights: 32B × 0.62 = 19.84 GB
  2. KV Cache (FP16 at 16K context): ~2.15 GB
  3. CUDA Runtime Overhead: 1.1 + (0.045 × 19.84) = 1.99 GB
  4. Total Footprint: 19.84 + 2.15 + 1.99 = 23.98 GB

At 23.98 GB on a 24 GB card, Windows/Linux desktop compositing would push the model over the VRAM limit. By switching the KV cache from FP16 to Q8_0, total memory drops to 22.90 GB, keeping 100% of layers inside VRAM and achieving roughly 30.6 tokens/second.

Actionable Optimization Strategies

  • Prioritize Q4_K_M or Q5_K_M over FP16: 4-bit K-quantization retains over 98.5% of baseline benchmark accuracy while cutting VRAM requirements by nearly 70%.
  • Enable Quantized KV Cache for Long Contexts: Whenever running 32K+ context windows for RAG or coding agents, enable Q8_0 KV cache quantization to prevent silent RAM offloading.
  • Leverage Prompt Caching in Cloud APIs: If your application sends a repeated system prompt or knowledge document across requests, enabling prompt caching on Claude, OpenAI, Gemini, or DeepSeek cuts input token charges by 50% to 90%.

Frequently Asked Questions

How much VRAM is required to run a 70B LLM locally?

Running a 70B parameter model in 4-bit quantization (Q4_K_M at ~0.62 bytes per parameter) requires approximately 43.4 GB for model weights alone, plus 2.5 to 6 GB for KV cache and CUDA/Metal runtime overhead—making a 48 GB dual-GPU setup (such as Dual RTX 3090) or a 64 GB Apple Silicon Mac ideal.

Why does memory bandwidth determine LLM token generation speed?

Autoregressive token generation (batch size 1) is memory-bandwidth bound rather than compute bound. For every single token generated, the GPU must read the entire active model weights from VRAM into compute cores, making GB/s bandwidth the primary speed bottleneck.

How much VRAM does a long context window (32K or 128K) consume?

KV cache grows linearly with context length. On a 32B or 70B model, expanding context from 4,096 to 32,768 tokens in FP16 KV precision can consume an extra 4 GB to 10 GB of VRAM. Enabling Q8_0 or Q4_0 KV cache quantization cuts this footprint by 50% to 75%.

When is self-hosting a local GPU cheaper than paying for Cloud AI APIs?

If your workload processes fewer than 5 to 10 million tokens per day, serverless APIs like DeepSeek-V3, Gemini 2.5 Flash, or GPT-4o-mini usually cost less than GPU electricity and hardware depreciation. Self-hosting becomes cost-effective at high sustained throughput or when strict air-gapped data privacy is mandatory.

What happens if an LLM exceeds my GPU VRAM capacity?

Inference engines like llama.cpp offload excess transformer layers to system DDR4/DDR5 RAM over the PCIe bus. Because system RAM bandwidth (~40–90 GB/s) is 5x to 15x slower than dedicated GDDR6X/HBM VRAM, generation speed drops sharply to 1–4 tokens per second.
